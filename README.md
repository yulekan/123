# Учёт спецодежды и СИЗ — исправленная версия

Отдельная папка с переработанным кодом. Исходный проект рядом не изменялся,
поэтому можно сравнить поведения и перенести базу.

## Запуск

Требования: Windows, .NET Framework 4.8.

```powershell
# из этой папки
dotnet build
dotnet run
```

Либо открыть `PPEAccounting.sln` в Visual Studio 2022 и нажать F5.
Пакет `System.Data.SQLite.Core` восстанавливается автоматически.

Дополнительные ключи командной строки:

| Ключ | Что делает |
|---|---|
| `--empty` | создать базу без демонстрационных данных |
| `--selftest` | прогнать дымовой тест бизнес-логики без интерфейса, результат в `%TEMP%\ppe-selftest.log`, код возврата 0/1 |
| `--screenshots` | снять иллюстрации экранов в `%TEMP%\ppe-shots` |

## Где теперь лежит база

`%LOCALAPPDATA%\PPEAccounting\ppe.db`

Раньше файл лежал в `bin\Debug` и удалялся при «Очистить/Пересобрать», а при установке
в `Program Files` запись была бы вообще запрещена. При первом запуске исправленная
версия **один раз копирует** старый `ppe.db` из папки программы и показывает об этом
сообщение. Удалите файл из `%LOCALAPPDATA%`, чтобы начать с чистой базы.

Режим WAL создаёт рядом служебные файлы `ppe.db-wal` и `ppe.db-shm` — это нормально,
копировать/архивировать базу лучше вместе с ними либо после закрытия программы.

## Что исправлено

### Ошибки, которые портили данные

| Проблема в исходном коде | Решение | Где смотреть |
|---|---|---|
| `Db.LastInsertId()` открывал **новое** соединение, а `last_insert_rowid()` в SQLite привязан к соединению → всегда некорректный Id | `Insert` читает `SQLiteConnection.LastInsertRowId` на том же соединении | `Data/Database.cs`, `Data/SqlExtensions.cs` |
| Выдача СИЗ не была атомарной: `INSERT` и списание остатка — разные соединения, без транзакции | Одна транзакция на всю выдачу | `Services/IssueService.cs` |
| Остаток списывался без защиты от минуса (check-then-act) | Атомарное `UPDATE ... WHERE StockQty >= @qty`, отказ при 0 затронутых строк | `Services/IssueService.cs` |
| Возврат СИЗ не возвращал остаток на склад — склад «таял» | Возврат в одной транзакции меняет и журнал, и остаток | `Services/IssueService.cs` |
| База в `bin\Debug`, терялась при пересборке | `%LOCALAPPDATA%` + однократный перенос старой базы | `Data/DbPathResolver.cs` |
| Дубли норм: `UNIQUE` не было, `FindNorm` брал `LIMIT 1` | Уникальный индекс + проверка перед вставкой + автосхлопывание дублей при миграции | `Data/SchemaMigrator.cs`, `Data/NormRepository.cs` |
| `GetNormQtyPerYear` падал на `DBNull` | `SqlValue.ToInt` корректно обрабатывает `DBNull` | `Data/SqlValue.cs` |

### Бизнес-логика

- Лимит выдачи считается **за скользящие 12 месяцев**, а не за календарный год.
- Возвращённые позиции не расходуют лимит (и объясняется, почему).
- Остаток меняется **только документами**: приход, выдача, возврат. Ручное редактирование
  остатка в карточке убрано, потому что оно расходилось с историей.
- Оживлена таблица `Supply`: кнопка «Приход» на складе создаёт документ и увеличивает остаток
  в одной транзакции.
- Удаление сотрудника или вида СИЗ с историей заблокировано; для сотрудников остаётся
  мягкое увольнение (галочка «Активен»).
- Норму можно изменить, повторная норма для той же пары «СИЗ + должность» отклоняется.
- Появилась дата выдачи (раньше всегда «сегодня»).
- Валидация выполняется **до** закрытия диалога — введённые данные не теряются.

### Архитектура и поддерживаемость

- `Db` заменён на `Database`; репозитории и сервисы — обычные классы с интерфейсами,
  собираются в `AppServices`. Благодаря этому `IssueService` можно прогнать на временной базе
  (см. `--selftest`).
- `IssueRepository`-«бог» разбит на `EmployeeRepository`, `PpeItemRepository`,
  `NormRepository`, `LookupRepository`; работа с журналом — в `IssueService`.
- Таблицы в UI привязаны к типизированным моделям (`Data/Models.cs`) вместо `DataTable`,
  поэтому в формах больше нет `Convert.ToInt32(DataRowView)` и подобного;
  сортировка по клику на заголовок сохранена (`SortableBindingList`).
- Копипаста вынесена в `UiFactory` (таблица, заголовки, комбобоксы, привязка),
  `DialogForm` (каркас диалога) и `UiTheme` (цвета, шрифты, кнопки).
- Статусы (`Выдана`/`Возвращена`) — константы `IssueStatus`, а не строки по коду.
- `RoundedButton`: подсветка хранится в свойстве, а не в `Tag`; `Pen` освобождается;
  утечка дочерних форм устранена — формы кэшируются и освобождаются в `Dispose`.
- Добавлены миграции через `PRAGMA user_version`, индексы, WAL, `busy_timeout`,
  внешние ключи, `CHECK`-ограничения для новых баз.
- Даты пишутся/читаются через `InvariantCulture`; включено DPI-масштабирование
  (`PerMonitorV2`); непойманные исключения показываются одним диалогом.

## Проверка

```
PPEAccounting.exe --selftest
```

40 проверок: норма, лимит, отказ сверх нормы, отказ сверх остатка, возврат остатка,
повторный возврат, приход, отметка получения, корректность Id, уникальность норм,
запрет удаления, создание всех форм, колонки и сортировка таблиц, отсутствие таблицы
учётных записей после миграции. Текущий результат — `РЕЗУЛЬТАТ: OK`.

## Структура

```
PPEAccounting.sln
PPEAccounting.csproj          SDK-style, net48, WinForms
Program.cs                    точка входа, ключи, глобальные обработчики
AppServices.cs                сборка зависимостей
Data/                         БД: соединение, миграции, модели, репозитории
Services/                     бизнес-правила: выдача/возврат, приход
Ui/                           тема, кнопка, таблица, каркас диалога
Forms/                        экраны: главная, сотрудники, склад, нормы, журнал, отчёты, журнал действий
Reports/                      печатные формы: личная карточка, ведомости, журнал выдачи
Diagnostics/SelfTest.cs       дымовой тест без интерфейса
Diagnostics/ScreenshotRunner.cs  съёмка иллюстраций для отчёта
```

## Что сознательно осталось за рамками

- Справочник цехов пока из демо-данных; должность можно добавить кнопкой «+» рядом с
  выбором должности (в карточке сотрудника и в диалоге нормы), поставщика — из карточки
  СИЗ. Для полноценной эксплуатации нужен отдельный экран справочников.
- Печатные формы ограничены пятью отчётами (личная карточка, ведомости, журнал выдачи);
  акты списания и произвольные отчёты за период не формируются.
- Нет авторизации и разграничения доступа; база не шифруется — для персональных данных
  сотрудников это стоит учесть при внедрении.
- Возврат оформляется целиком по строке журнала (без частичного количества).
- Нет отдельного проекта модульных тестов и CI — вместо этого дымовой тест в приложении.
